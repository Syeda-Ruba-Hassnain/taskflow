# 09 — Testing

## 1. Testing Framework

**Vitest 4.1.10** with `@vitest/coverage-v8` for coverage, configured in `vitest.config.mts`:

```ts
test: {
  environment: "node",
  include: ["**/*.test.ts"],
  exclude: ["node_modules/**", ".next/**"],
  coverage: {
    provider: "v8",
    reporter: ["text", "html", "json-summary"],
    include: [
      "lib/ai/**", "app/api/ai/**",
      "lib/task/**", "app/api/tasks/**",
      "lib/services/**",
      "app/api/register/**", "app/api/change-password/**",
      "app/api/delete-account/**", "app/api/forgot-password/**",
      "app/api/reset-password/**", "app/api/verify-email/**",
      "app/api/resend-verification/**", "app/api/profile/**",
    ],
  },
},
```

`vite-tsconfig-paths` is used so tests can use the same `@/` path alias as application code.

## 4. Testing Methodology

### 4.1 Unit Testing

The majority of the suite is unit-level: individual functions/classes tested in isolation with mocked dependencies. Examples: `lib/ai/config.test.ts` (env-var resolution edge cases — missing key, invalid timeout value, caching behavior), `lib/ai/parser.test.ts` (fence-stripping, malformed JSON), `lib/ai/validator.test.ts` (Zod schema acceptance/rejection), `lib/ai/mappers/task.mapper.test.ts`, `lib/task/task-validator.test.ts`, `lib/ai/context/context.manager.test.ts`, `lib/ai/context/context.store.test.ts` (including TTL/expiry behavior).

### 4.2 Integration Testing

`lib/ai/integration.test.ts` exercises the **full AI pipeline** — from a raw transcript-equivalent input through parsing, validation, context resolution, and execution — rather than only testing each stage in isolation. This is the test file most directly responsible for confidence that the pipeline's stages compose correctly, not just that each stage is individually correct.

### 4.3 API / Route Testing

Every route handler with meaningful logic has a colocated `route.test.ts` (`app/api/ai/intent/route.test.ts`, `app/api/tasks/route.test.ts`, `app/api/tasks/[id]/route.test.ts`, `app/api/register/route.test.ts`, `app/api/change-password/route.test.ts`, `app/api/delete-account/route.test.ts`, `app/api/forgot-password/route.test.ts`, `app/api/reset-password/route.test.ts`, `app/api/verify-email/route.test.ts`, `app/api/resend-verification/route.test.ts`, `app/api/profile/route.test.ts`) — 10 of the 13 API routes have a dedicated test file. The two without one are the NextAuth catch-all (`app/api/auth/[...nextauth]/route.ts`, effectively a thin wrapper around the library-tested `auth.ts` config) and the health check (`app/api/health/route.ts`).

### 4.4 Validation Testing

`lib/task/task-validator.test.ts` and `lib/ai/validator.test.ts` specifically target edge cases in field validation: boundary lengths (exactly `MAX_TITLE_LENGTH`, one over), allow-list rejection, whitespace-only input handling, and the documented REST-vs-AI due-date parsing divergence (Section 7 of [04-System-Design.md](./04-System-Design.md)).

### 4.5 AI-Specific Testing

Beyond the integration test (4.2), the AI subsystem has the most granular test coverage in the codebase: separate test files for the client, config, both context files, both mapper files, the executor, the messages builder, the parser, and the validator — nine dedicated AI test files in addition to the integration test and the route test, reflecting that this subsystem (untrusted external input, non-deterministic upstream) carries the highest correctness risk in the application.

### 4.6 Error Handling Tests

Error paths are tested alongside their success paths throughout — e.g., `auth.service.test.ts` covers wrong-password, unverified-email, and rate-limited branches, not just successful sign-in; `app/api/tasks/[id]/route.test.ts` covers the not-found/not-owned `404` path.

## 5. Continuous Integration

`.github/workflows/ci.yml` runs on every `push` and `pull_request`:

```yaml
env:
  DATABASE_URL: "postgresql://ci:ci@localhost:5432/ci"
  AUTH_SECRET: "ci-placeholder-secret"
  RESEND_API_KEY: "ci-placeholder-key"
  NEXT_PUBLIC_APP_URL: "http://localhost:3000"

jobs:
  build-and-test:
    steps:
      - checkout
      - setup-node (v20, npm cache)
      - npm ci
      - npm test
      - npm run lint
      - npx tsc --noEmit
      - npm run build
```

The workflow's own comment states these are build-time-only placeholder values: nothing in CI talks to a real database or email provider (tests mock those boundaries; `next build` never executes a route handler), so the placeholders exist purely to satisfy module-level `process.env` reads at import/build time. This is the exact sequence reproduced manually in this documentation pass (Section 2), and it matched CI's presumed behavior — all four steps passed.

**Gap:** CI has no step that would catch the missing-migrations issue documented in [05-Database-Design.md § 7](./05-Database-Design.md#7-migration-strategy), because CI never provisions or connects to a real database — a `DATABASE_URL` is set only so `import`-time reads don't throw, not to actually run migrations against it.
