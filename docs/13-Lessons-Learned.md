# 13 — Lessons Learned

This document is framed as a retrospective, but every "lesson" below is anchored to a specific, verifiable artifact in the codebase — a comment, a test, a structural pattern — not a generic engineering aphorism. Where a lesson is this documentation effort's own conclusion rather than one the codebase states about itself, that distinction is made explicit.

## 1. Technical Challenges

**Reconciling two entry points into the same data model, built at different times.** The AI assistant was layered onto an already-working REST task API. The `TODO(Phase 2.2)` comments in `lib/task/task-validator.ts` are a direct record of the friction this caused: the REST due-date parser and the AI due-date parser had already diverged in strictness (REST truncates longer ISO strings; the AI path requires an exact match) by the time this was noticed, and the decision was to document and preserve the divergence rather than risk changing either call site's established behavior under time pressure. **Lesson:** when a second consumer is added to code that wasn't designed with multiple consumers in mind, divergences will happen before anyone deliberately decides to unify or diverge — the discipline that matters is *noticing and documenting* the divergence (as was done here) rather than either silently living with an unexplained inconsistency or unifying it reflexively without checking both call sites' existing guarantees.

**Security hardening vs. rendering strategy.** Adding a per-request CSP nonce is the textbook way to avoid `'unsafe-inline'` in a script-src policy. The `next.config.ts` comments show this was considered and explicitly rejected for this project, because implementing it would require introducing `middleware.ts`, which would force several currently-static pages into dynamic rendering — a change judged out of scope for what was framed as a security-only pass. **Lesson:** a "pure" security fix is rarely actually isolated from the rest of the architecture; the right call here was to name the tradeoff explicitly in a comment rather than either silently accepting weaker CSP or silently absorbing an unplanned rendering-strategy change into a security-focused commit.

## 2. Architecture Decisions

**Sharing `TaskService` between REST and AI was the single highest-leverage architectural decision in the codebase.** It is not stated as a lesson anywhere in the code, but its consequences are visible everywhere: it's why the AI pipeline needed no independent validation logic, why a task created by voice is indistinguishable from one created by hand, and why the test suite doesn't need a second, parallel set of task-business-rule tests for the AI path — the AI's own tests focus on parsing/context/execution dispatch, trusting `TaskService`'s already-tested behavior underneath. **Lesson:** when adding a new interface (voice/AI) to an existing capability, the highest-value architectural move is making the new interface a client of the existing business logic rather than a reimplementation of it — even when that means the new interface's code (the AI executor) is more of a thin adapter than a feature in its own right.

**Repository-layer ownership scoping, not route-layer.** `TaskRepository.updateForUser`/`deleteForUser` bake the `userId` filter into the same query as the mutation, rather than trusting a check performed one layer up. **Lesson:** the same authorization rule enforced in two places (once as a defense, once redundantly) is weaker in practice than the same rule enforced in exactly one place that's structurally impossible to bypass — this codebase chose the latter, and it shows in how short and uniform every task route handler's ownership-related code is (there isn't any; it's not the route's job).

## 3. AI Integration Lessons

**Defend against LLM output at both the prompt and the code level, not just one.** The system prompt explicitly instructs the model never to use Markdown fences or add explanatory text — and `lib/ai/parser.ts` *also* strips fences defensively and handles non-JSON output gracefully, rather than trusting the prompt instruction to hold 100% of the time. **Lesson:** prompt instructions are a strong bias on LLM behavior, not a guarantee; the codebase treats them exactly that way — as the first line of defense, backed by code that assumes the model will occasionally not comply.

**Push deterministic computation out of the model, into code.** Relative date resolution ("tomorrow," "next Monday") is computed server-side in `lib/ai/prompt.ts` and handed to the model as concrete, already-resolved examples — the model is not asked to compute date arithmetic itself. **Lesson:** for any sub-task within an LLM's job that has a deterministic, verifiable answer, computing it in code and showing the model the answer (rather than asking the model to derive it) removes an entire category of LLM error at effectively zero cost.

**In-memory state is the easiest thing to get right for a demo and the easiest thing to get wrong for production.** `AIContextStore`'s `Map`-based conversational memory works perfectly on a single running process — and the codebase does not currently claim otherwise; this documentation set is the first place the horizontal-scaling implication is written down explicitly (see [07-AI-Module.md § 10](./07-AI-Module.md#10-context-manager--conversation-memory)). **Lesson (specifically for the deploying team, not yet acted on):** a feature that "just works" locally and in a single-instance deployment can carry a hidden environment-topology assumption that only surfaces once the deployment target changes — worth auditing for explicitly before scaling out, not after.

## 4. Testing Lessons

**The subsystem with the highest correctness risk (untrusted external input, non-deterministic upstream) got the most granular test coverage, and this appears deliberate, not incidental.** Nine dedicated AI test files plus an integration test, versus a single test file for most REST routes. **Lesson:** test investment tracked risk in this codebase, rather than being spread evenly by file count — a good instinct that shows in the coverage report (`app/api/ai/intent/route.ts` at 97.14%, comparable to or higher than most REST routes).

**Coverage scoping was deliberate, but its boundary wasn't obvious from the number alone.** `vitest.config.mts`'s `coverage.include` excludes `components/**` and `Dashboard.tsx` entirely — the 95.7% figure is real but easy to misread as whole-application coverage if you don't check the config. **Lesson (for this documentation effort specifically):** always verify what a coverage percentage's denominator actually is before citing it — this SRS/testing document only reports the figure alongside its scope for exactly this reason (see [09-Testing.md § 3](./09-Testing.md#3-coverage-statistics)).

## 5. Database Lessons

**A schema without committed migrations is a debt that's invisible until the exact moment it matters.** Every day-to-day development workflow — `npm run dev`, `npm test`, even `npm run build` — works fine while the schema is defined only in `schema.prisma`. This gap is now resolved in the repository by committing the baseline migration history in `prisma/migrations/20260731112025_init/migration.sql`. **Lesson:** "the build passes" and "the tests pass" are necessary but not sufficient signals that a system is deployable — and the committed migration history is the missing artifact that closes that gap.

## 6. Performance Lessons

**A documented, reasoned removal beats an undocumented one.** The Phase 7 removal of the redundant ownership pre-check in `PATCH /api/tasks/:id` is accompanied by a comment explaining exactly what changed, why, and what the one observable behavioral difference is (a request with both a nonexistent task ID *and* invalid field data now surfaces via the update's own 404 rather than an earlier one). **Lesson:** a performance optimization that changes an edge case's exact failure path is a legitimate tradeoff — but only if it's written down, so a future reader debugging that exact edge case doesn't mistake documented, intentional behavior for a regression.

## 7. Security Lessons

**Silence can be a security control.** `forgot-password` and `resend-verification` return byte-for-byte identical responses regardless of internal state (account exists or not, already verified or not) — a small, easy-to-get-wrong detail (many implementations leak this via subtly different wording or timing) that this codebase gets right consistently across both endpoints. **Lesson:** anti-enumeration isn't one control, it's a discipline applied per-endpoint, and it's worth explicitly testing for (as this codebase's route tests do) rather than trusting it to remain true as an endpoint evolves.

**Re-authentication for destructive actions is cheap insurance against a narrow but real threat model.** Requiring the current password for `change-password` and `delete-account`, even with a valid session already established, specifically defends against a stolen/XSS'd session cookie being used to fully take over or destroy an account. **Lesson:** "the user is already authenticated" and "this specific request is really from the user, right now" are different guarantees — the gap between them matters most exactly on the highest-consequence actions, which is where this codebase chose to spend the UX cost of asking again.

## 8. Software Engineering Lessons

**Self-documenting, dated, named-phase comments are a lightweight but effective substitute for a separate architectural decision record (ADR) log.** This codebase has no `docs/adr/` directory, yet a careful reader can reconstruct *why* several non-obvious decisions were made (Section 2 above) purely from inline comments referencing specific audit phases. **Lesson:** the discipline of writing the *why*, not just the *what*, directly at the point of change is valuable independent of whether it lives in a dedicated ADR file or a code comment — what matters is that it exists at all and survives as long as the code it explains.

**Consistency has a maintenance cost, and one exception doesn't erase the value of the rule.** `Dashboard.tsx` is the one place in this codebase that departs from the otherwise-thorough decomposition pattern used everywhere else. Its existence doesn't undermine the value of that pattern elsewhere — if anything, it makes the pattern's absence in this one file more visible and more clearly an outlier worth eventually addressing, rather than "just how this codebase is." **Lesson:** a single well-contained exception to an otherwise-consistent convention is a normal, honest state for a real codebase to be in — worth naming precisely (as [04-System-Design.md § 3](./04-System-Design.md#3-dashboard-module) does), not worth treating as either invisible or catastrophic.
